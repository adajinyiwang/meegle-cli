# AI SDLC 协作套件（dida-sdlc）使用文档

> 相关文档：[meegle-cli 总 README](../README.zh-CN.md) ｜ 架构与命令参考：[sdlc/README.md](../sdlc/README.md)

> 面向使用 Claude Code 的产品/开发/测试同事。dida-sdlc 只负责**流程推进**——
> 产物落仓、飞书项目节点推进、任务同步、交接与收尾；**怎么写 PRD、怎么写代码、
> 怎么设计用例是你自己的工作**，工具不管也不教。推荐用斜杠命令
> （`/sdlc-start` 等）触发流程——一眼就能分清当前是在推进流程还是在做实际工作。

## 0 · 首次安装（每台电脑一次）

前置：Git、Node ≥ 20；Windows 用户自带 Git Bash（装 Git 时就有）。

```bash
npx -y @didatravel-jinyi/meegle@latest install --host project.feishu.cn --lang zh
```

（私有化部署把 `--host` 换成你的租户域名；无浏览器环境加 `--device-code`。）

- 向导一次装好：`meegle` 与 `sdlc` 两个全局命令、`meegle` 使用指南技能、6 个 `/sdlc-*` 薄入口 skill、共享规则 `~/.sdlc/skill-core.md`，并引导飞书登录。
- Windows 装完**重开终端**，cmd/PowerShell 即可直接用 `sdlc`（npm 自动生成 shim）。
- 装完自检：终端跑 `sdlc doctor`，或在对话里说「工具出问题了」。
- **首次使用**：第一条需要飞书的命令会转出浏览器飞书授权链接，点一次授权，之后全程自动（凭据由 meegle 官方托管，AI 与工具都碰不到）。
- 你参与的**业务仓库**若还没有 `.sdlc/` 目录：让仓库维护者跑一次 `sdlc init`（每仓一次，配置随 Git 共享给仓库里所有人）。

## 1 · 六个斜杠命令（推荐入口）

| 斜杠 | 用途 |
|---|---|
| `/sdlc-start <飞书需求链接或id>` | 进入 / 绑定 / 恢复需求 |
| `/sdlc-next` | 保存成果 / 提测交接 / 打回回退 |
| `/sdlc-done` | 需求收尾（归档、合并核验） |
| `/sdlc-status` | 看现状（只读快照） |
| `/sdlc-update` | 更新工具 / 环境自检 |
| `/sdlc-init` | 仓库接入（维护者用，每仓一次） |

推荐斜杠的理由：与实际工作清晰区分——**看到 `/sdlc-` 前缀就知道自己在推进流程**。说自然语言（「接需求」「保存一下」「提测」）同样有效，AI 会路由到同一条命令。

对话里你**不需要记任何 CLI 命令**：AI 用自然语言转述计划（如「创建需求分支并绑定」），你回「继续」它才执行；高频低风险动作（保存/交接）直接执行，出问题停下如实转述。

## 2 · 开发同事的一天

**① 接需求**

产品在飞书项目里把需求推进到开发节点，把需求链接发给你（或群里）。你对 Claude 说：

> /sdlc-start https://project.feishu.cn/dida/story/detail/7131581708

AI 会：核对飞书上这条需求的现状 → 建议创建需求分支并绑定本地档案 → **先把计划说给你听**
（建什么分支、放什么文件），你回「继续」它才执行。接手别人交接到一半的需求时，如果发现
飞书流程节点没跟上，它会建议补推到位——同样先说后做。

**② 拆任务（你的开发工作）**

任务清单你自己拆，或让 AI 帮你起草——这是正常开发工作，不归 sdlc 管。拆好的清单放进
`dev/tasks.md`（模板约定任务带编号和估分）。保存时 AI 会**自动同步到飞书**：带估分的任务
自动把你设为负责人、自动排期；后续新任务增量同步，重跑不会重复创建。

**③ 干活 → 顺手保存**

写完一块代码，或完成清单里的一项任务时：

> /sdlc-next

（说「保存一下」也行。）AI 会：提交当前成果并推送 → 同步任务勾选（你标记完成的清单项，
**自动在飞书项目上勾掉**，不用切去飞书点）→ 发布流程记录。保存是高频动作，直接执行
不打扰你；出问题它会停下来原样转述。

**④ 提测 / 交接**

开发完成时：

> /sdlc-next

（说「开发完成，提测」。）AI 会：勾掉该勾的任务 → 输出一条**预填好参数的 MR 创建链接**
→ 把飞书需求推进到测试节点。你只剩一个人工动作：**点开链接创建 MR**（工具不代建，创建后
把 MR 链接贴回对话，AI 记录归档）。最后它会生成一段交接话术，直接转发给测试同事。

**⑤ 测试打回 / 需求变更**

> /sdlc-next

（说「打回开发，原因是 xxx」。）AI 会把飞书节点回退到开发并留痕，分支与 MR 不变——继续
在原分支修，再走一次提测。

**⑥ 收尾**

测试通过、MR 合并后：

> /sdlc-done

AI 会：归档需求档案 → 若 MR 还没合，停在「待人工合并」并给你一段可转发的合并提醒 →
合并后核验收尾，飞书终态落位。它**不会在 MR 未合并时宣称已完成**。

## 3 · 测试同事

接手提测需求：`/sdlc-start <需求链接>` 恢复现场 → 从交接话术里拿到 MR 与测试要点
→ 测试产物（用例/报告）写完 `/sdlc-next` 保存落仓 → 不通过说「打回开发，原因是 xxx」
（`/sdlc-next`）→ 通过后 `/sdlc-done`。

## 4 · 产品同事

PRD 你自己写（或让 AI 帮你起草内容——那是内容工作），放进 `product/prd.md`。写完
`/sdlc-next` 保存落仓；说「交接给开发」时飞书节点推进到开发，交接话术自动生成转给开发。
需求中途变更说「需求变更」并描述变化，AI 留痕回退。

## 5 · 任何角色、任何时候

| 你说 | 发生什么 |
|---|---|
| 「现在什么情况」「需求进展」 | 只读快照：阶段、缺什么、MR 状态、下一步 |
| 「接需求 / 继续 xxx」 | 绑定或恢复某个需求的工作现场 |
| 「保存一下」 | 提交推送 + 同步任务勾选（高频，直通执行） |
| 「提测」「交接给 xxx」 | 任务同步 + MR 链接 + 飞书节点推进 |
| 「打回开发」「需求变更」 | 飞书节点回退，说明留痕 |
| 「需求收尾」「归档」 | 归档 + 待合并提醒 + 终态核验 |
| 「更新 sdlc」「工具出问题了」 | 版本升级 / 环境自检（先给计划再动） |

## 6 · 更新与排障

| 场景 | 做法 |
|---|---|
| 有新版本 | `/sdlc-update`（或说「更新 sdlc」）：执行 `npm i -g @didatravel-jinyi/meegle@latest` 并重铺薄入口与 skill-core；meegle 启动时的自动更新提示也会顺带刷新 |
| 怀疑工具异常 | 说「工具出问题了」——AI 跑环境自检并转述结论 |
| 登录失效 | 无需手动登录：命令自动转出飞书授权链接，点一次后自动续跑原命令 |

## 7 · 为什么可以放心让 AI 动飞书

- **先看后做**：除高频的保存/推进/任务同步直通外，写动作都先出计划、你确认才执行。
- **话术不吹牛**：只陈述已核实的事实——「待人工合并」就是还没合并，不会说成已完成。
- **重复执行无害**：同一个确认重发一遍，已做过的全部跳过，不会重复推进飞书节点。
- **权限即边界**：所有飞书操作用的是你本人的账号凭据——你能做什么，它才能做什么。
- **全程留痕**：每次推进/同步都记进随 Git 共享的流程记录，接手的人看得到完整历史。
